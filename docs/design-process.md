# ขั้นตอนออกแบบ (design)

> ประเภทเอกสาร: **how-to** — ใช้กับทุก agent (Hermes, Claude Code, Codex …) และคน
> เป้าหมาย: ไม่ว่าใครออกแบบ ต้องได้**ไฟล์ชุดเดียวกัน หัวข้อเดียวกัน ผ่านเกณฑ์เดียวกัน** — `make docs-check` ตรวจโครงสร้างให้อัตโนมัติ
> ทางลัดสำหรับ agent: skill `design` (`.agents/skills/design/SKILL.md`) ทำตามไฟล์นี้ทีละขั้น

## 1. ต้อง design เมื่อไร

| งาน | ต้อง design? |
|---|---|
| โปรเจกต์ใหม่ | **ต้อง** (`type: system`) ก่อนสร้าง repo หรือเขียนโค้ด |
| ฟีเจอร์ที่เข้า**ข้อใดข้อหนึ่ง**: entity/ตารางใหม่, บทบาทหรือสิทธิ์ใหม่/เปลี่ยนสิทธิ์เดิม, ผูกระบบภายนอก (SSO, API, อีเมล, LINE), import/ย้ายข้อมูล, เก็บข้อมูลส่วนบุคคลชนิดใหม่, ฟีเจอร์ AI, กลุ่มหน้าจอใหม่ (≥ 2 หน้า), คาดว่าเกิน 1 PR | **ต้อง** (`type: feature`) ก่อนเปิด PR โค้ด |
| ฟีเจอร์เล็ก (แก้/เพิ่มในตารางและสิทธิ์เดิม, 1 PR) | ไม่ต้อง — เขียนใน issue ว่า `design: ไม่ต้อง — <เหตุผล 1 บรรทัด>` |
| ไม่แน่ใจ | ถามคนก่อน ห้ามเดา |

## 2. ผลลัพธ์ (ปลายทางเดียวกันทุก agent)

| ไฟล์ | เมื่อไร | กติกา |
|---|---|---|
| `docs/design/<slug>.md` | ทุกครั้ง | คัดลอกจาก `docs/design/template.md` ครบทุกหัวข้อ — โปรเจกต์ใหม่ใช้ `system.md`, ฟีเจอร์ใช้ `<เลข epic>-<slug>.md` (เช่น `58-asset-cmdb.md`) |
| `CONTEXT.md` | มีคำใหม่/คำกำกวม | คำไทย + `โค้ด:` + `en:` + นิยาม + _ห้ามใช้_ |
| `docs/adr/NNNN-<slug>.md` | การตัดสินใจที่ครบ 3 ข้อใน `docs/adr/README.md` | สถานะ `proposed` จนคนอนุมัติ + เพิ่มในดัชนี ADR |
| `docs/architecture.md` | โปรเจกต์ใหม่ หรือเพิ่ม/ลบ container, ระบบภายนอก | แก้รูป C4 ระดับ 1–2 |
| `docs/design/README.md` | ทุกครั้ง | เพิ่มแถวในดัชนี design |
| GitHub issue | epic ก่อนเริ่ม, issue ย่อยหลังอนุมัติ | epic มี label `design`; issue ย่อยลิงก์ epic + ไฟล์ design |

ทั้งหมดอยู่ใน **PR เอกสารอย่างเดียว** ชื่อ `docs(design): <slug>` body มี `Refs #<epic>` — ห้ามมีโค้ดใน PR นี้

**ยังไม่มี repo (โปรเจกต์ใหม่):** ร่างในโฟลเดอร์ที่โครงสร้างเหมือน repo (`CONTEXT.md`, `docs/design/system.md`, `docs/adr/`, `docs/architecture.md`) — ทีม Hermes ใช้ `/home/opc/projects/_design/<ชื่อ>/` — ตอน scaffold คัดลอกทับตาม path เดิมได้ทันที

## 3. ลำดับขั้น

### 3.0 เริ่ม

1. เปิด epic issue (label `design`) — โปรเจกต์ใหม่ที่ยังไม่มี repo ข้ามข้อนี้ไปเปิดหลัง scaffold
2. สร้าง `docs/design/<slug>.md` จาก template ตั้ง `status: draft`
3. อ่าน `CONTEXT.md`, `docs/adr/`, `docs/architecture.md`, design เดิมที่เกี่ยวข้อง — ห้ามถามสิ่งที่มีคำตอบอยู่แล้ว

### 3.1 สัมภาษณ์เป็นรอบ (design tree)

มองการตัดสินใจเป็นต้นไม้ แต่ละรอบถาม**ทุกคำถามที่ตอบได้แล้วตอนนี้**ในข้อความเดียว (คำถามที่ขึ้นกับคำตอบข้ออื่น → รอบถัดไป) รูปแบบตายตัว:

```
รอบ 2 — สิทธิ์และสถานะ
Q1 — ใครปิดใบแจ้งซ่อมได้: ผู้แจ้ง / ช่างที่รับงาน / Admin
  แนะนำ: ช่างที่รับงานและ Admin — ผู้แจ้งยืนยันผลแทนการปิดเอง
Q2 — เหตุการณ์ขอบ: ช่างลาออกระหว่างมีงานค้าง งานเป็นของใคร
  แนะนำ: กลับเป็น "รอมอบหมาย" และแจ้ง Admin
ตอบแยกข้อได้ เช่น "Q2: ให้ Admin เลือกช่างใหม่" หรือ "ตามแนะนำทั้งหมด"
```

- ทุกข้อมีคำตอบที่แนะนำพร้อมเหตุผลสั้น
- ทุกรอบมีเหตุการณ์ขอบ 1–2 ข้อ
- ข้อเท็จจริงที่หาเองได้ (เวอร์ชัน, ราคา, สเปก, library, ระบบเดิม) **ห้ามถาม** — ไปหาเอง และถามข้ออื่นต่อระหว่างรอ
- คำกำกวมหรือขัดกับ `CONTEXT.md` ทักทันทีและเสนอคำเดียว
- ห้ามถือว่าคนตกลงในสิ่งที่ไม่ได้ถาม — สิ่งที่สมมติไว้ใส่หัวข้อ 14 (คำถามที่ยังเปิด)
- **จบแต่ละรอบ: เขียนคำตอบลงไฟล์ทันที** แล้วสรุปสั้น: ตกลงอะไร, อยู่หัวข้อไหน, เหลือกิ่งไหน

### 3.2 กิ่งที่ต้องเดินครบ

ลำดับเป็นแนวทาง ถามตาม frontier ตัวเลขในวงเล็บคือหัวข้อใน `docs/design/template.md`

- **A ความต้องการและขนาด** (1, 2, 9): ผู้ใช้/บทบาท/จำนวน, ปัญหาที่แก้, นอกขอบเขต, ผู้ใช้พร้อมกันสูงสุด, ปริมาณข้อมูล/ไฟล์ต่อเดือน, งานหนัก (รายงาน, ประมวลผลไฟล์, ค้นหา, งานเบื้องหลัง)
- **B Business logic** (3, 4, 5): user journey ต่อบทบาท, ตารางสิทธิ์ role × action (รวมทางอ้อม: ยกเลิก, รวมรายการ, คืนสถานะ, งานเบื้องหลัง), สถานะ + การเปลี่ยนสถานะ + ใครเปลี่ยนได้, ฟังก์ชัน MVP / ทีหลัง
  → **จุดอนุมัติ 1: ขอบเขต MVP**
- **C Stack** (15, ADR-0001 — เฉพาะ `type: system`): เทียบ 2–3 ทางพร้อมลิงก์อ้างอิงและวันที่
  - เกณฑ์ production: image multi-arch (amd64 + arm64), ขนาดบีบอัดเริ่มต้น ≤ ~150 MB (GHCR ของ org Free ~500 MB รวมทุกโปรเจกต์)
  - เกณฑ์ dev: เครื่อง dev เป็น ARM64 ใช้ร่วมหลายโปรเจกต์ → ค่าเริ่มต้นต่อ service `cpus: 1.0` / `mem_limit: 1g` (เกินได้เมื่อมีเหตุผลในงบทรัพยากร)
  - เวอร์ชันและ license ตาม `docs/dependencies.md` (แกนหลักสาย N-1 + วัน EOL, library ≥ 14 วัน)
  - ต้องรองรับ: หลายภาษา + light/dark (`docs/ui.md`), test/e2e ง่าย, library ยังมีคนดูแล
  - ชุด skill ของ stack 3–6 ตัว แต่ละตัวมี `source:` — มีชุดสำเร็จรูปใน `docs/stacks/skills/<stack>/` ให้ใช้ชุดนั้น แยก "คัดลอก" กับ "ต้องเขียนใหม่" ให้ชัด; ชุดที่อนุมัติบันทึกใน ADR-0001
  - ทางเลือกที่มีสูตรใน `docs/stacks/` มาก่อน; ทางที่ไม่มีสูตรต้องบอกคนตอนเทียบว่า "ต้องเขียนสูตรก่อน หรือคนรับความเสี่ยงและบันทึกใน ADR-0001" (`docs/stacks/README.md` วิธีใช้ ข้อ 1)
  - งบทรัพยากรต่อ service (RAM/CPU ขณะรันจริง) + ขนาด image
  → **จุดอนุมัติ 2: stack + DB + UI + skill + งบทรัพยากร**
- **D Data model** (6): ตาราง, ฟิลด์หลัก, ความสัมพันธ์, unique/บังคับ/index, ชื่อตาม `CONTEXT.md`, ER diagram (mermaid `erDiagram`), ตาราง audit
- **E หน้าจอ** (7): รายการหน้าจอ, wireframe ทุกหน้า, สถานะว่าง/โหลด/error/ไม่มีสิทธิ์, ข้อความยาวภาษาอังกฤษ, mobile
- **F ข้อกำหนดที่ไม่ใช่ฟังก์ชัน** (8, 9): การแจ้งเตือน (เหตุการณ์ → ใคร → ช่องทาง), login/SSO, session timeout, เหตุการณ์ใน audit log + ระยะเก็บ, ภาษาที่รองรับ + ปี พ.ศ./ค.ศ., theme, ข้อมูลส่วนบุคคล (อะไร เก็บนานเท่าไร ใครเห็น), RPO/RTO, ฟีเจอร์ AI (`docs/ai-agents.md` หัวข้อ 8)
- **G Threat model** (10): STRIDE ทุกตัวอักษร กับทางเข้าใหม่ (route, ฟอร์ม, ไฟล์, webhook, งานเบื้องหลัง) — โดยเฉพาะ id ที่รับจากผู้ใช้ (`.agents/rules/api.md`)
- **H ส่งมอบ** (11, 12, 13, 15): เหตุการณ์ขอบที่ตัดสินแล้ว, import/ย้ายข้อมูล + rollback, แผนแตก issue เป็นชิ้นที่ merge ได้เอง (ชิ้นละ 1 PR ทำงานได้ end-to-end ขนาดตามหัวข้อ 4), โปรเจกต์ใหม่: ชื่อ repo, dev URL, เครื่อง production, ข้อมูล seed
  → **จุดอนุมัติ 3 (system): เริ่มสร้างโปรเจกต์** / **(feature): อนุมัติ design**

### 3.3 ตรวจก่อนขออนุมัติ

1. `make docs-check` ผ่าน (โครงสร้าง, หัวข้อครบ, ดัชนี)
2. ไล่เช็คลิสต์ด้วยตัวเอง:
   - [ ] ทุกหัวข้อมีเนื้อหา หรือเขียน `ไม่เกี่ยว — <เหตุผล>`
   - [ ] ทุกบทบาทใน CONTEXT.md อยู่ในตารางสิทธิ์ และทุก action ในหน้าจอ/journey อยู่ในตารางสิทธิ์
   - [ ] ทุกสถานะใน diagram มีทางเข้าและทางออก (ยกเว้นสถานะจบ)
   - [ ] ทุกตาราง/ฟิลด์ใหม่ใช้ชื่อตาม CONTEXT.md
   - [ ] threat model มีครบ 6 ตัวอักษร และทุกข้อมีวิธีกัน + test
   - [ ] แผนส่งมอบ: ทุกชิ้น merge ได้เอง ไม่เกินเกณฑ์ขนาดในหัวข้อ 4 และชิ้นแรกเล็กที่สุดที่ใช้งานได้
   - [ ] หัวข้อ 14 ว่าง (หรือเหลือเฉพาะเรื่องที่คนตกลงให้ตัดสินทีหลัง พร้อมกำหนดว่าเมื่อไร)
3. เปลี่ยน `status: proposed` แล้วเปิด PR เอกสาร — รายงานคนพร้อมลิงก์ PR และสรุปทางเลือกที่ยังเปิด

### 3.4 อนุมัติ

- คนตอบอนุมัติ → commit ใน PR เดียวกัน: design `status: approved`, `approved-by`, `date`; ADR ที่เกี่ยวเป็น `accepted` → คน merge
- `make docs-check` บังคับ: design ที่ `approved` ต้องไม่มี `TODO` และไม่มีคำถามค้างในหัวข้อ 14

### 3.5 หลังอนุมัติ

- เปิด issue ย่อยตามหัวข้อ 13 ทีละชิ้น — แต่ละใบลิงก์ epic และ `docs/design/<slug>.md#13-แผนส่งมอบ`; acceptance criteria มาจาก journey, ตารางสิทธิ์ และ threat model **เฉพาะของชิ้นนั้น** (ห้ามดึงตาราง/หน้าจอของชิ้นถัดไปมารวม)
- ชิ้นใดเกินเกณฑ์ในหัวข้อ 4 (แม้ design อนุมัติแล้ว) → แตกต่อก่อนเปิด issue แล้วแก้ตารางหัวข้อ 13 ใน PR ของชิ้นแรกที่ทำ
- PR โค้ดใส่ `Design: docs/design/<slug>.md` ใน description
- โค้ดต้องตรงกับ design ที่อนุมัติ — ถ้าระหว่างทำพบว่าต้องเปลี่ยน: แก้ไฟล์ design (+ ADR ถ้าเข้าเกณฑ์) **ใน PR เดียวกับโค้ด** และบอกคนใน PR ว่าเปลี่ยนอะไร
- design เก่าที่ถูกแทน: `status: superseded by <ไฟล์ใหม่>` ห้ามลบ

## 4. ขนาดชิ้นงาน (1 ชิ้น = 1 issue = 1 PR)

ชิ้นหนึ่งต้องเข้าทุกข้อ — เกินข้อใดให้แตกต่อ (PR ใหญ่รีวิวยาก และ agent มักทำไม่จบในรอบเดียว):

- โค้ดที่ไม่ใช่ test ไม่เกิน ~800 บรรทัดที่เพิ่ม/แก้ (ไม่นับ test/e2e, ไฟล์ที่ generate เช่น `*_templ.go`, lockfile, ไฟล์ข้อความแปล `locales/`, เอกสาร `*.md`/`docs/`, `.agents/`) — วัดด้วย `make pr-size` (`scripts/pr-size.sh` เทียบกับ main รวมไฟล์ที่ยังไม่ commit) ระหว่างทำทุกครั้งที่เสร็จแต่ละส่วน ไม่ใช่รอตอนจบ
- migration ไม่เกิน 1 ไฟล์ และสร้างเฉพาะตาราง/คอลัมน์ที่ชิ้นนั้นใช้ — ตารางของชิ้นถัดไปอยู่ใน migration ของชิ้นนั้น
- กลุ่มหน้าจอ/route ใหม่ไม่เกิน 1 กลุ่ม (เช่น "จัดการหมวดหมู่" หรือ "CRUD บทความ" ไม่ใช่ทั้งสองอย่าง)
- dependency ใหม่ไม่เกิน 1 ชุด (ตัวที่ต้องใช้คู่กัน เช่น markdown + sanitizer นับเป็นชุดเดียว)
- มี unit test และ e2e ของสิ่งที่ผู้ใช้เห็นในชิ้นนั้นเอง — ห้ามรวม e2e ไว้ชิ้นท้าย
- ชิ้นแรก = schema ขั้นต่ำ + หน้าจอแรกที่ใช้งานได้

ในหัวข้อ 13 ของ design เขียนแต่ละชิ้นเป็นรายการสิ่งที่ส่ง (ตาราง, route, หน้าจอ, dependency) เพื่อให้ตรวจขนาดได้ก่อนอนุมัติ
